    Validation rules

    owatch validate checks a requirements directory against the rules below and reports each problem with the file, line and column it was found at. It makes no network calls, so it costs nothing to run as often as you like — and it is the cheapest way to find a problem before owatch assess would bill for one.

    $ owatch validate ./requirements
Success! The requirements in ./requirements are valid.

    Every rule has a name, which appears in brackets on the diagnostic it raised:

    ╷
│ Error: Requirement id is used more than once (duplicate-id)
│
│   on core.yaml line 1, column 7:
│    1: - id: REQ_001
│
│ The id "REQ_001" is already used by the requirement at api.yaml line 1.
│ An id must name exactly one requirement within a directory.
╵
1 error and 0 warnings.

    owatch assess runs the same rules before it requests anything, so a directory that fails validate will not be assessed.

    The requirement schema

    A requirement holds four fields, and no others:

    - id: REQ_001                                    # required
  requirement: The system shall do the thing.    # required
  tags: [cli, assess]                            # optional
  status: accepted                               # optional; the only value

    An id may hold letters, digits, _ and -. Ids must be unique within a requirements directory, but the same id may be used in a different requirements directory elsewhere.

    The rules

    Rule Severity Raised when
    invalid-yaml Error A requirements file cannot be parsed as YAML. The other files are still checked.
    invalid-document Error A requirements file's top-level value is not a list.
    missing-id Error A requirement has no id, or its id is empty.
    invalid-id Error An id holds a character other than a letter, a digit, _ or -.
    duplicate-id Error An id is used by more than one requirement in the directory. Raised against each use after the first.
    missing-requirement Error A requirement has no requirement text, or its text is empty.
    invalid-tag Error A tag is empty, or holds whitespace.
    invalid-status Error A status holds a value other than accepted.
    unknown-field Error A requirement holds a field the schema does not define.
    no-requirements Error The directory holds requirements files, but none of them holds a requirement.

    unknown-field is the rule worth knowing about. A mistyped key is valid YAML and parses without complaint, so without this rule a requirement would quietly lose its tags with nothing to show that it happened:

    - id: REQ_001
  requirement: The system shall do the thing.
  tag: cli          # unknown-field: "tag" is ignored, the requirement has no tags

    Tags are compared exactly, so API and api are two different tags. That is deliberate: only you know whether your system means them as one.

    Writing a report file

    --output-file writes the diagnostics as YAML, for a CI job to archive or parse. The report is written whether or not anything was found, so a passing run still produces an artefact:

    $ owatch validate ./requirements --output-file validation.yaml
validation.yaml

    valid: false
error_count: 1
warning_count: 0
diagnostics:
- severity: error
  rule: duplicate-id
  summary: Requirement id is used more than once
  detail: The id "REQ_001" is already used by the requirement at api.yaml line 1.
  range:
    filename: core.yaml
    start:
      line: 1
      column: 7
    end:
      line: 1
      column: 14

    The diagnostics go to standard error and the report path to standard output, so the path can be piped somewhere without the diagnostics arriving with it.

    Exit status

    validate exits non-zero if any rule raised an error, and zero otherwise. Warnings do not fail a run. No rule raises a warning today; the severity exists because it is a property of a diagnostic rather than of the command, so the report format will not change when the first advisory rule is added.
